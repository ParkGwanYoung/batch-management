# 배치 운영 관리 시스템

배치 작업을 웹에서 등록하고 실행하며, 실행 결과와 오류 이력을 한곳에서 확인할 수 있도록 만든 개인 프로젝트입니다.

- 개발 기간: 2026.07 ~ 2026.09.29
- 개발 인원: 1명
- 담당 범위: 설계, 백엔드 API, 관리 화면, DB, AWS 배포 및 CI/CD 구성
- 시연 주소: http://pgy-batch.duckdns.org/login

## 프로젝트를 시작한 배경

협력사 소속으로 SKT T world biz 개발·운영을 담당하고 있습니다. 폐쇄망 환경에서 배치 일정과 실행 결과를 한눈에 볼 수 있는 관리 화면 없이, 명령어로 배치를 확인하고 로그와 문자 알림으로 결과를 확인해 왔습니다.

운영하다 보면 어떤 작업이 실패했고, 어떤 데이터에서 문제가 생겼는지부터 확인하게 됩니다. 작업 전체를 중단해야 하는 오류인지, Skip으로 처리한 데이터 오류인지도 화면에서 바로 확인할 수 있으면 좋겠다고 생각했습니다.

이런 경험을 바탕으로 작업 등록부터 실행, 결과와 오류 조회까지 웹에서 확인하고 운영하기 편한 시스템을 만들었습니다.

| 기능 | 내용 |
| --- | --- |
| 관리자 인증 | JWT 기반 로그인 및 API 인증 |

현재 실행 대상으로는 **회원 데이터 처리 샘플 Job**을 연결했습니다. 활성 회원의 이메일 누락을 검사하고, 정상 데이터의 동기화 시각을 갱신합니다.

등록된 여러 작업은 같은 샘플 Job을 호출합니다. 작업 이름에 표시된 청구·수납·회원 삭제나 외부 시스템 동기화는 실제 업무 로직으로 구현하지 않았습니다. 이번 프로젝트에서는 배치를 실행하고 결과와 오류를 관리하는 기능에 집중했습니다.

## 요청 처리와 배포 구조

브라우저 요청은 EC2의 Nginx로 들어옵니다. Nginx는 React 화면을 제공하고, `/api` 요청을 Spring Boot backend 컨테이너로 전달합니다.

frontend와 backend는 Docker Compose로 관리합니다. 작업 설정과 실행 결과는 RDS MySQL에 저장합니다.

GitHub Actions에서는 MySQL 테스트 환경을 준비한 뒤 Gradle 테스트, React 빌드, Docker 빌드를 수행합니다. 모두 성공하면 EC2의 self-hosted runner에서 소스를 받아 Docker Compose로 배포합니다. DB 접속 정보는 환경변수로 전달했습니다.

실무에서는 정해진 환경에서 Jenkins를 재실행하거나 WAS에 접속해 로그를 확인했습니다. 이번에는 코드 반영부터 테스트와 EC2 배포까지 직접 연결해 보고 싶어 배포 환경도 함께 구성했습니다.

## 실행과 오류를 처리한 방식

### 실행 상태와 이력

수동 실행 요청은 `WAITING` 상태로 생성하고, 실행 조건을 확인한 뒤 `RUNNING`으로 변경합니다. 배치가 끝나면 최종 상태와 처리 건수, Skip 건수를 저장합니다.

화면에서 실행 결과와 로그, 오류 항목을 함께 볼 수 있도록 Spring Batch 메타데이터와 별도로 실행 이력을 관리했습니다.

### Cron 변경과 예약 실행

작업별 Cron 표현식을 DB에 저장하고, 활성 작업의 다음 실행 시각을 계산합니다. Cron을 수정하면 다음 예약 시각을 새 일정으로 변경하며, 실행 직전에도 활성 상태와 Cron 변경 여부를 다시 확인합니다. 예약 실행 이력은 `SCHEDULE`로 구분합니다.

예정 시각이 지났다면 한 번 실행하고, 완료 시각 이후의 다음 일정으로 이동합니다. 실행 중 지나간 예약을 모두 연속으로 실행하지 않도록 했으며, 서버 재시작 후에는 미래 일정부터 계산합니다.

### Retry와 Skip

이메일이 없는 회원은 다시 시도해도 입력값이 바뀌지 않으므로 `InvalidMemberDataException`으로 구분해 Skip 처리했습니다. 해당 데이터의 ID와 오류 내용을 실행 ID에 연결해 저장합니다.

일시적인 DB LOCK 상황에서 `CannotAcquireLockException`이 발생하면 다시 시도하도록 설정했습니다.

| 설정 | 값 |
| --- | ---: |
| Chunk 크기 | 100 |
| Reader 페이지 크기 | 100 |
| Retry 한도 설정 | 3 |
| Skip 한도 설정 | 5 |

처리 건수는 Spring Batch의 Step 결과에서 가져옵니다. `successCount`는 `writeCount`, `failCount`는 `skipCount`에 대응합니다. 따라서 전체 실행 상태가 `SUCCESS`여도 Skip된 데이터가 존재할 수 있습니다. 화면의 실패 건수는 Skip된 데이터 건수를 의미합니다.

배치 결과를 먼저 저장한 뒤 Slack 알림을 보내도록 해서, 알림 전송이 실패해도 실행 결과는 유지되게 했습니다.

### 동일 작업의 중복 시작 제어

수동 실행과 예약 실행이 동시에 요청될 수 있어, DB LOCK을 사용해 같은 작업의 실행 조건을 한 요청씩 확인하도록 했습니다. 실행 조건 확인과 `RUNNING` 상태 저장은 하나의 트랜잭션으로 처리합니다.

같은 작업이 실행 중이면 요청을 거절하고, `RUNNING` 상태를 저장한 뒤에는 LOCK을 해제하고 실제 배치를 실행합니다. 이미 완료된 실행을 다시 요청해도 기존 실행 결과가 변경되지 않도록 처리했습니다.

## 개발하면서 해결한 문제

### 배치 실행 중 트랜잭션 오류

배치를 실행하면서 `Existing transaction detected in JobRepository` 오류가 발생했습니다. 배치 실행을 호출하는 메서드에 `@Transactional`이 적용돼 있어, 이미 트랜잭션이 시작된 상태에서 Spring Batch를 실행한 것이 원인이었습니다.

배치 실행을 감싸던 `@Transactional`을 제거하고, 실행 상태를 저장하는 처리와 실제 배치를 실행하는 처리를 구분했습니다.

### Skip 오류 내역 저장 중 NullPointerException

Skip된 데이터의 오류 내용을 저장할 때 `stepExecution`이 null인 상태여서 실행 ID를 가져오지 못했습니다.

`beforeStep()`에서 실행 정보를 받을 수 있도록 리스너 등록을 보완했습니다. Step 시작 시 실행 정보를 먼저 받은 뒤, Skip된 데이터의 ID와 오류 내용을 해당 실행 이력에 연결해 저장하도록 수정했습니다.

### 로컬과 배포 환경의 차이

- **배치 테이블 조회 실패:** RDS의 테이블명은 소문자인데 Spring Batch가 대문자로 조회하고 있었습니다. 배치 메타데이터 테이블명을 대문자로 변경한 뒤 정상 실행을 확인했습니다.
- **실행 이력 조회 오류:** DTO 변환 중 지연 로딩된 작업 정보에 접근하면서 `LazyInitializationException`이 발생했습니다. 필요한 작업 정보를 `JOIN FETCH`로 함께 조회하도록 수정했습니다.
- **실행 시간 차이:** 배포 환경에서 UTC 기준으로 기록되던 시간을 `-Duser.timezone=Asia/Seoul` 설정으로 맞췄습니다.

## 목록 조회 API 부하 테스트

요청량이 늘어났을 때 목록 조회의 응답 시간과 실패 여부를 확인하기 위해 k6 테스트를 진행했습니다.

JWT 인증 후 `GET /api/batch-jobs?page=0&size=10`을 호출했습니다. 각 테스트는 1분 동안 진행했고, 반복당 목록 조회 요청을 1회 보냈습니다. 아래 RPS는 목표 요청률입니다.

실행 순서는 **200 → 100 → 150 → 200 재테스트 → 400 → 800 → 600 RPS**입니다.

| 목표 RPS | 목록 요청 수 | 목록 p95 | HTTP 실패율 | 미시작 반복 |
| --- | ---: | ---: | ---: | ---: |
| 200 최초 | 11,342 | 4,572.80 ms | 0% | 658 |
| 100 | 6,000 | 25.28 ms | 0% | 0 |
| 150 | 9,001 | 25.01 ms | 0% | 0 |
| 200 재테스트 | 12,001 | 23.76 ms | 0% | 0 |
| 400 | 24,001 | 40.53 ms | 0% | 0 |
| 800 | 47,200 | 2,210.73 ms | 20.79% | 801 |
| 600 | 35,784 | 507.51 ms | 0% | 217 |

p95는 요청의 95%가 해당 시간 이내에 응답했다는 의미입니다. 목록 요청 수는 로그인 1회를 제외했고, HTTP 실패율은 로그인을 포함한 전체 요청 기준입니다. 미시작 반복은 k6가 예정된 시점에 시작하지 못한 반복 수입니다.

400 RPS에서는 실패와 미시작 반복 없이 실행을 마쳤습니다. 600 RPS에서는 HTTP 실패율이 0%였지만, 333건이 1초 이상 걸렸고 미시작 반복도 217회 발생했습니다. 800 RPS에서는 전체 HTTP 요청 47,201건 중 9,811건이 실패했습니다.

첫 200 RPS와 재테스트 결과에도 차이가 있어 두 결과를 함께 기록했습니다. 테스트 구간의 서버 지표도 확인했으며, 캡처에 표시된 CPU 사용률은 EC2 약 19%, RDS 약 22.6%까지 올라갔고 RDS 연결 수는 약 10개였습니다.

이번 프로젝트에서는 동일한 첫 페이지 10건을 대상으로 요청률별 응답 시간, 실패율, 미시작 반복을 비교하고 서버 자원 상태를 함께 확인하는 데까지 진행했습니다.

## 직접 만들면서 느낀 점

처음에는 작업을 등록하고 실행 결과를 저장하면 될 거라고 생각했습니다. 하지만 화면과 기능을 연결하다 보니 수동 실행인지 예약 실행인지, 언제 시작하고 끝났는지, 어떤 데이터에서 오류가 났는지까지 필요했습니다. 실행 로그만으로 부족한 부분은 항목별 오류 테이블과 조회 API를 추가하며 설계를 보완했습니다.

실무에서는 이미 구성된 환경에서 소스를 수정하고 배포 결과를 확인했다면, 이번에는 Docker부터 EC2와 RDS 연결, GitHub Actions 배포까지 직접 구성했습니다. 로컬에서 되던 기능이 배포 환경에서는 다르게 동작하는 문제를 겪으며 코드와 실행 환경을 함께 확인하게 됐습니다.

트랜잭션을 어디까지 적용해야 하는지도 처음에는 낯설었습니다. 실행 상태를 저장하는 처리와 실제 배치를 실행하는 처리를 구분하면서 이해할 수 있었고, 발생한 오류와 수정 이유를 정리하며 필요한 개념을 익혔습니다.

## 다음에 개선하고 싶은 부분

현재는 배치가 끝날 때까지 응답을 기다립니다. 실행 요청을 받으면 실행 ID를 먼저 반환하고, 배치는 비동기로 처리하도록 개선하고 싶습니다. 화면에서는 실행 ID로 진행 상태와 결과를 확인하도록 할 계획입니다.

서로 다른 작업을 동시에 실행하되, 서버에 부담이 가지 않도록 실행 개수와 대기 개수도 제한하려고 합니다. 이 과정에서 기존 중복 실행 방지와 결과 저장이 정상적으로 동작하는지도 함께 확인할 예정입니다.

이후에는 회원 동기화나 통계 집계처럼 작업 이름에 맞는 실제 처리 기능도 채우고 싶습니다. 서로 다른 배치가 정해진 일정에 따라 실제 데이터를 처리하는 자동화 시스템으로 확장하고, 직접 운영해 보고 싶습니다.
